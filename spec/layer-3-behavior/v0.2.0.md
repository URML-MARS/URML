# URML Layer 3 — Behavior Composition — v0.2.0

**Spec version:** 0.2.0 (pre-stable; per-artifact semver, breaking changes
allowed before 1.0.0)
**Status:** Normative. This is the specification document for Layer 3.
**Originating decision record:** The base composition grammar has no dedicated
RFC. It was introduced in
[RFC-0002](../../docs/rfcs/0002-initial-primitive-vocabulary.md), whose
Unresolved Questions explicitly defer "the formal Layer-3 grammar" to a future
Layer-3 RFC that was never filed. The grammar was instead implemented directly
(validator schema + ros2-runtime executor) and described informally in this
layer's README. The two fleet-addressing nodes `on` and `barrier` (§2.5–2.6)
were added by
[RFC-0286](../../docs/rfcs/0286-multi-robot-fleet-addressing.md). This document
is the normative statement of the grammar, transcribed from the shipped
implementation. Where a future Layer-3 RFC revisits a decision, it updates this
document in the same change.

**Changes since v0.1.0.** Two additive composition nodes — `on` (scope a
subtree to a fleet member) and `barrier` (synchronize members) — for
multi-robot programs. A single-robot program uses neither and behaves exactly
as under v0.1.0.

---

## 1. Scope and conventions

Layer 3 is the grammar for assembling Layer-2 primitives into behaviors. A
URML program is a single recursive tree of composition nodes whose leaves are
Layer-2 primitive invocations. Layer 3 specifies the operators, the
error-handling model, the variable system, and the condition-expression
sublanguage. It introduces no primitives (those are Layer 2) and is not a
general-purpose programming language: no user-defined functions, no unbounded
loops, no closures. Every URML program is statically checkable by
construction.

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY**
are to be interpreted as in RFC 2119.

This document specifies the four core composition operators (`sequence`,
`branch`, `parallel`, `retry`), the two fleet-addressing nodes (`on`,
`barrier`; §2.5–2.6), the `on_error` model, the variable-binding system, and
the condition-expression grammar. A conformant runtime MUST execute each per
its documented semantics; the validator MUST reject every program that
violates a documented static rule, and execution MUST NOT begin for a rejected
program.

### 1.1 Program structure

A URML program (`URMLProgram`) is:

```yaml
urml: "0.1"          # optional spec-version pin; default "0.1"
profile: home         # an identifier, or a list when the program straddles profiles
behavior: <node>      # exactly one root behavior node (the tree below)
description: <string>  # optional
```

`behavior` is exactly one **BehaviorOrStep** node. There is one root; a
program is a single tree, not a list of trees. A fleet program pairs an
ordinary single-root program like this with a roster (Layer 1 §6); the `on`
nodes inside the tree name roster members.

### 1.2 BehaviorOrStep

Every node in the tree is either a **composition node** (`type: sequence |
branch | parallel | retry | on | barrier`) or a **Step** (a single Layer-2
primitive invocation, the single-key-dict surface `{move_to: {...}}`).
Composition nodes nest recursively: a `sequence` MAY contain a `parallel` whose
branch is a `retry`, and so on, to any depth. A Step MUST carry exactly one
primitive.

Every composition node MAY carry two common fields:

- `on_error` — one of `abort_and_report | continue | retry` (§3).
- `label` — an optional human-readable annotation; semantically inert.

## 2. Composition operators

### 2.1 `sequence`

```yaml
type: sequence
steps: [ <node>, ... ]      # MUST contain at least one node
on_error: <policy>          # optional
```

**Semantics.** Execute `steps` in declared order, each starting after the
previous completes. The sequence completes successfully when its last step
completes successfully. If a step fails, the sequence's `on_error` policy
(§3) decides what happens; the default (no `on_error`) behaves as
`abort_and_report`. `steps` MUST be non-empty (an empty sequence is rejected
at validation by the schema's `min_length: 1`).

### 2.2 `branch`

```yaml
type: branch
condition: <expression>     # a §5 condition expression
if_true: <node>             # required
if_false: <node>            # optional
on_error: <policy>          # optional
```

**Semantics.** Evaluate `condition` (§5) once. If true, execute `if_true`. If
false, execute `if_false` if present; if `if_false` is absent and the
condition is false, the branch is a successful no-op. `if_true`/`if_false`
are each a single BehaviorOrStep (use a nested `sequence` for multiple steps,
as in [`examples/home/patient-fetch`](../../examples/home/patient-fetch.urml.yaml)).

### 2.3 `parallel`

```yaml
type: parallel
branches: [ <node>, <node>, ... ]   # MUST contain at least two nodes
complete_when: all | any | first_to_succeed   # default: all
on_error: <policy>                  # optional
```

**Semantics.** Execute `branches` concurrently. The block completes per
`complete_when`:

- `all` (default) — completes when every branch has completed; fails if any
  branch fails.
- `any` — completes when any branch completes (success or failure).
- `first_to_succeed` — completes as soon as one branch succeeds; the runtime
  MAY short-circuit the others (see
  [`examples/drone/parallel-watch`](../../examples/drone/parallel-watch.urml.yaml)).

`branches` MUST contain at least two nodes (schema `min_length: 2`).
`parallel` prescribes that the branches happen and gives the runtime freedom
to coordinate them; it does NOT prescribe single-robot motion coordination —
that is a Layer-0 concern. In a fleet, two `on` branches of one `parallel` that
drive different members to the same place are caught statically (Layer 1 §6.3,
`fleet.concurrent_shared_workspace`).

### 2.4 `retry`

```yaml
type: retry
behavior: <node>            # required; the node to repeat
max_attempts: <int>         # required; MUST be > 0
until: <expression>         # optional; a §5 condition expression
on_error: <policy>          # optional
```

**Semantics.** Execute `behavior`. If it succeeds and `until` is absent, the
retry completes. If `until` is present, it is evaluated after each attempt;
the retry completes when `until` is true. Otherwise `behavior` is re-executed,
up to `max_attempts` total attempts. If the bound is reached without success
(or without `until` becoming true), the retry fails. `max_attempts` MUST be a
positive integer (schema `gt: 0`); **a retry always terminates by
construction** — there is no unbounded loop in URML.

### 2.5 `on` (fleet member scope — RFC-0286)

```yaml
type: on
member: <identifier>        # a roster member handle (Layer 1 §6)
body: <node>                # exactly one BehaviorOrStep
on_error: <policy>          # optional
```

**Semantics.** Dispatch every primitive beneath this node to the named roster
member's robot. `on` has exactly one child (`body`), so it preserves the
single-root-tree invariant: it is a tagged wrapper, not a fan-out. A program
with no `on` node is a single-robot program and behaves exactly as before this
RFC; in a multi-member fleet, a step that sits outside any `on` scope is
rejected (`fleet.undeclared_member`). The named `member` MUST be declared in
the roster, and the primitives under it MUST be supported by that member's
manifest (Layer 1 §6.3). `on` nodes nest inside the ordinary operators — most
commonly two `on` nodes as the branches of a `parallel`, to run two robots at
once.

### 2.6 `barrier` (fleet synchronization — RFC-0286)

```yaml
type: barrier
members: [ <identifier>, <identifier>, ... ]   # at least two, unique
on_error: <policy>          # optional
```

**Semantics.** A leaf node: execution does not proceed past a `barrier` until
every named member has reached it. This is the synchronization primitive that
makes a handoff safe — the receiving robot does not act until the delivering
robot has arrived and stopped. `members` MUST contain at least two unique
handles (schema `min_length: 2` plus a uniqueness check), each declared in the
roster, and each MUST declare the `peer_link` connectivity role (Layer 1
§2.10), or the program is rejected (`fleet.barrier_missing_peer_link`).

## 3. The `on_error` model

`on_error` on a composition node is exactly one of:

- `abort_and_report` — on a child failure, stop and surface the failure
  upward. This is the default when `on_error` is omitted.
- `continue` — on a child failure, treat it as handled and proceed (in a
  `sequence`, move to the next step).
- `retry` — on a child failure, re-attempt (the bounded-retry disposition;
  pair with a `retry` node for an explicit attempt bound).

In a fleet, `on_error` is scoped like any other node: a policy on a node inside
an `on` subtree governs that member's failures; a `barrier` with
`abort_and_report` (the default) surfaces a member's failure-to-arrive to the
whole program.

**Honest reconciliation.** This layer's README sketches a fourth form,
`substitute(other_behavior)` (a contingency behavior). It is **not** part of
v0.2: the shipped `OnError` enumeration is exactly the three values above. A
contingency behavior is expressed by composing `branch` (or a
`first_to_succeed` `parallel`) explicitly. `substitute` remains a candidate
for a future Layer-3 RFC; until one accepts it, it is not normative and a
runtime MUST NOT be expected to honor it.

## 4. The variable system

`store_as: <name>` on a binding-producing primitive binds that primitive's
result to `name`. `$name` (and dotted `$name.field.subfield`) references it in
a later step's arguments or in a condition expression.

**Producer types.** A binding carries a stable type tag determined by the
producing primitive:

| Producer primitive | Binding type |
|---|---|
| `detect` | `object` |
| `scan` | `survey_result` |
| `measure` | `measurement` |
| `capture` | `media_handle` |
| `listen` | `transcription` |
| `wait_for` | `wait_result` |

Any other primitive's `store_as` carries `unknown`.

**Static rules the validator enforces (Pass 4 — variable bindings):**

1. **Unique `store_as`.** A name MUST NOT be bound more than once anywhere in
   the program (no shadowing). Error code `binding.duplicate_store_as`.
2. **Reference resolution.** A `$ref` MUST resolve to a name bound *earlier in
   the linear walk order* of the tree. Unbound references are
   `binding.unresolved_reference`. In v0.2, `branch` / `parallel` / `retry`
   boundaries are treated **permissively** — a name bound inside one arm is
   visible to later walk-order positions. Proper definite-assignment analysis
   (a name bound only on one side of a `branch` is not guaranteed downstream)
   is a documented future tightening, not enforced in v0.2.
3. **Cross-primitive type compatibility.** When a consumer dereferences a
   `$ref`, the producer's binding type MUST be one the consumer accepts;
   otherwise `binding.type_mismatch`. `$ref.field` chains are accepted
   whenever the producer is a structured payload; field-level type checking is
   deferred to a future RFC. `report.attachments` is intentionally permissive
   (accepts any producer type) for diagnostics.

## 5. Condition expressions

`branch.condition` and `retry.until` are condition-expression strings. This
spec version defines the normative subset:

- **Boolean literals:** `true`, `false`, `always`, `never`.
- **Numbers:** integer and float, optionally signed (`1`, `1.5`, `-3`).
- **Strings:** single- or double-quoted (`"red"`, `'red'`).
- **Variable references:** `$name`, `$name.field`, `$name.field.subfield`.
- **Comparisons:** `==` `!=` `<` `>` `<=` `>=`.
- **Boolean operators:** `and`, `or`, `not`.
- **Parentheses:** `(expr)`.

**Semantics.** An unbound `$name` evaluates to a falsy null; attribute access
through a null is null (so `$missing.field` is just falsy, never an error).
This makes `$detected` usable as "was something bound?". **Arithmetic is
intentionally excluded** — compute a value in the program, bind it, and
compare the binding. Examples:

```
true
$target.confidence > 0.9
$target.attributes.color == "red"
$found and $target.confidence > 0.5
```

**Honest reconciliation — static checking.** The validator does **not**
statically parse `condition` / `until`. A malformed or unsupported-construct
expression is detected at *execution* time (the runtime condition evaluator
raises an error naming the offending construct), not at validation time. Static
well-formedness and static type-checking of condition expressions are a
documented future tightening.

## 6. What is and is not statically enforced in v0.2

To keep the spec honest about the validator's actual reach:

**Enforced at validation time:**

- Structural bounds (schema): non-empty `sequence`, `parallel` with ≥2
  branches, `retry.max_attempts > 0` (so every retry terminates), exactly one
  primitive per Step, `on_error` restricted to the three enumerated values,
  single root behavior, `on` with exactly one body, `barrier` with ≥2 unique
  members.
- Pass-4 binding rules (§4): unique `store_as`, reference resolution (linear
  walk order), cross-primitive producer/consumer type compatibility.
- Cross-robot fleet rules (Layer 1 §6.3): member declaration, per-member
  capability, concurrent-shared-workspace, and barrier peer-link.

**Deferred (named in the README as goals; NOT enforced in v0.2):**

- Static condition-expression well-formedness and type-checking (§5).
- Definite-assignment analysis across `branch` / `parallel` / `retry` arms
  (§4 rule 2).
- No-unreachable-branch and no-dangling-variable beyond the linear-walk
  approximation.
- A JSON-LD encoding equivalent to the canonical YAML (YAML is the only
  normative surface).

A future Layer-3 RFC tightens these; until then a runtime and toolchain MUST
NOT assume they are caught before execution.

## 7. Link loss is not a Layer-3 operator (RFC-0006)

[RFC-0006](../../docs/rfcs/0006-connectivity-and-link-loss.md) deliberately
adds no composition operator for connectivity. Link-loss behavior is a
deployment-time declaration in the safety envelope's `link_loss_policy`,
statically validated (Pass 2 / Pass 3) against the Layer-1 `connectivity:`
block. A connectivity-aware program is an ordinary composed program; it needs
no new Layer-3 vocabulary. This is the same composition-over-expansion
discipline Layer 2 applies to primitives.

## 8. Conformance and versioning

A conformant runtime, given a valid program:

- MUST execute `sequence`, `branch`, `parallel` (all three `complete_when`
  modes), `retry`, and Step nodes per §2.
- MUST, for a fleet program, dispatch each `on` subtree to its named member and
  hold execution at a `barrier` until every named member arrives (§2.5–2.6).
- MUST honor the `on_error` policy of §3.
- MUST resolve `$ref` bindings and evaluate §5 condition expressions per their
  documented semantics.

The machine-checkable expression of these requirements is the conformance
suite (`/conformance/fixtures/`, including the multi-robot lane
`fixtures/fleet/`); per-construct coverage of spec → schema → reference impl →
conformance fixture → runnable example is tracked in
[`docs/spec-coverage.md`](../../docs/spec-coverage.md).

This document is `layer-3-behavior@0.2.0`. Pre-`1.0.0`, breaking changes are
allowed but MUST go through a Layer-3 RFC that updates this document in the
same change.
