# URML Layer 1 — Hardware Abstraction (Capability Manifest) — v0.1.0

**Spec version:** 0.1.0 (pre-stable; per-artifact semver, breaking changes
allowed before 1.0.0)
**Status:** Normative. This is the specification document for Layer 1.
**Originating decision records:** The base manifest tracks
[RFC-0002](../../docs/rfcs/0002-initial-primitive-vocabulary.md)
(`manifest_version: "0.1"`). The `provenance:` block was added by
[RFC-0003](../../docs/rfcs/0003-us-alignment.md) /
[RFC-0004](../../docs/rfcs/0004-compliance-policy.md); its compliance-policy
evaluation is specified normatively in the sibling
[`policy.md`](policy.md). The `connectivity:` block was added by
[RFC-0006](../../docs/rfcs/0006-connectivity-and-link-loss.md). This document
is the consolidated normative statement of the manifest schema, transcribed
from the shipped validator.

## 1. Scope and conventions

Layer 1 is how a robot **declares what it can do**. A URML-compatible robot
ships one *capability manifest*: a small, machine-readable document the
validator consumes (alongside a program and a safety envelope) to decide,
before any actuator moves, whether this robot can execute a given program.

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY**
are to be interpreted as in RFC 2119.

Layer 1 is a thin capability layer **on top of** existing structure standards,
not a replacement for them. It is substrate-neutral: a robot running ROS 2,
PX4, AUTOSAR, OPC UA Robotics, or a vendor SDK declares the same capabilities
the same way. It declares *baseline* capability, not runtime state, not sensor
data, not world-model contents, and not what a primitive does (Layer 2) or how
behaviors compose (Layer 3).

The canonical surface is YAML. Every model below forbids unknown fields
(`extra: forbid`): a manifest with an undeclared key is rejected, not
silently ignored.

### 1.1 Shared types

- **Identifier** — a string matching `^[a-z][a-z0-9_]*$`, length 1–64
  (snake_case). Used for every `name`/`id`/role.
- **Pose** — `{x, y, z?, yaw?, pitch?, roll?}`; `x` and `y` are required, the
  rest optional. Always interpreted in a named `frame`.

### 1.2 Manifest envelope vs. safety envelope (a boundary)

This document specifies the **capability manifest** — the robot's
self-declaration. The **safety envelope** is a separate, deployment-time
artifact (its schema is `envelope.py`, its defaults documented per profile in
[`spec/profiles/`](../profiles/)). The validator's Pass 3 conjoins manifest
limits with the active envelope (strictest wins). Layer 1 references the
envelope; it does not contain it. The README's older "what goes here" list
folded the envelope schema under Layer 1; the shipped split is as stated here.

## 2. The capability manifest

```yaml
manifest_version: "0.1"     # fixed; only "0.1" is accepted in this spec version
robot_id: <identifier>      # required
description: <string>       # optional

frames: [ ... ]             # declared coordinate frames
declared_locations: [ ... ] # named places in the world model
declared_events: [ ... ]    # event identifiers wait_for / link rules may name

mobility: { ... }           # optional capability block
manipulation: { ... }       # optional capability block
perception: { ... }         # optional capability block

docking_stations: [ ... ]   # declared stations and their services
outputs: { named_endpoints: [ ... ] }   # report destinations

provenance: { ... }         # optional; RFC-0004 compliance (see policy.md)
connectivity: { ... }       # optional; RFC-0006 abstract link roles
```

`manifest_version` MUST be the literal `"0.1"`. `robot_id` MUST be present.
All capability blocks are individually optional; a program that uses a
primitive whose capability the manifest does not declare is rejected at Pass 2
with a structured error naming the primitive, the missing field, and the
suggested addition.

### 2.1 `frames`

A list of declared coordinate frames. Each: `name` (Identifier) and optional
`parent` (Identifier; the root frame has `parent: null`). Every `frame`
referenced by a `pose`, a `declared_location`, or a `docking_station` MUST
resolve to a declared frame. URML does **not** in v0.1 cross-check frames
against a referenced URDF/SDF (see §5).

### 2.2 `declared_locations`

Named places programs reference by name (`move_to: { location: kitchen }`).
Each: `name`, `pose`, `frame`, optional `description`. A named location used
by a program MUST resolve here (or against the active world model).

### 2.3 `declared_events`

A list of event Identifiers. `wait_for(condition.event: ...)` and an
RFC-0006 link-loss rule may only name events declared here.

### 2.4 `mobility`

Required by `move_to`, `dock`, `hover`, `scan` (area survey), and
profile-specific motion. Fields:

- `drive_type` — one of `differential`, `omnidirectional`, `ackermann`,
  `tracked`, `multirotor`, `fixed_wing`, `vtol`, `manipulator_base`,
  `underwater_thrusters`.
- `max_velocity` — m/s, ≥ 0, required.
- `max_payload` — kg, ≥ 0, optional.
- `station_keeping` — bool (default `false`); MUST be `true` for `hover`.
- `service_ceiling` — m, ≥ 0, optional; required for aerial profiles and
  checked by `take_off` / aerial `scan`.

### 2.5 `manipulation`

Required by `grasp`, `release`. Fields: `arm_count` (int ≥ 0); `grippers`
(list); `reachable_workspace_m` (≥ 0, optional). Each **Gripper**: `name`;
`kind` ∈ `pneumatic | servo_electric | vacuum | magnetic | compliant`;
`force_min_n` (≥ 0); `force_max_n` (> 0); `accepted_classes` (list of
Identifiers); `movable` (bool, default `true`). `grasp` is rejected unless a
gripper's declared force range contains the requested force and its
`accepted_classes` contains the target's object class.

### 2.6 `perception`

Required by `detect`, `scan`, `measure`, `capture`, and
`wait_for(condition.sensor_threshold: ...)`. Fields:

- `cameras` — each: `name`, `movable` (default `false`), `supports_photo`
  (default `true`), `supports_video`/`supports_stream` (default `false`),
  `max_resolution`. `capture(target: ...)` against a fixed camera is rejected
  statically.
- `sensors` — each: `name`; `measurement_type` ∈ `distance | temperature |
  weight | pressure | humidity | depth | wind_speed | current | voltage |
  speech | custom`; optional `range_min`/`range_max`/`units`.
- `object_vocabulary` — Identifiers `detect.object` MUST be drawn from.

### 2.7 `docking_stations`

Each: `name`, `pose`, `frame`, `services` (list of Identifiers; default
`["park"]`). Core services: `park`, `charge`; profile-extensible
(`swap_battery`, `swap_tool`, …). `dock(at, service)` is rejected unless the
target station declares the requested service.

### 2.8 `outputs`

`named_endpoints` — Identifiers a `report(to: <endpoint>)` may target. `user`,
`log`, and `caller` are universal and need no declaration; `speak` requires
`speech` declared here.

### 2.9 `provenance` (optional — RFC-0004)

Opt-in hardware-provenance declaration. **Absent ⇒ Pass 5 is a no-op for the
manifest** (compliance enforcement is opt-in; the default validator ships
US-federal rules active, but a manifest that does not opt in is exempt).

```yaml
provenance:
  manifest_attestation: self_declared   # self_declared | third_party_audited | cryptographically_signed
  attestation_uri: <uri|null>
  components:
    - id: <identifier>
      role: critical                    # critical | non_critical | informational
      vendor: <string>
      country_of_origin: <ISO-3166-1-alpha-2 | unknown>
      country_of_final_assembly: <ISO-3166-1-alpha-2 | unknown>
      hbom_ref:                         # optional
        format: <string>               # e.g. cyclonedx-1.7
        uri: <uri>
        sha256: <64-hex | null>        # required when uri is local
```

The *policy* evaluated against this block (which countries/attestations/roles
pass) is specified normatively in [`policy.md`](policy.md); it is not
re-specified here. What URML does **not** do, normatively: it does not fetch
the HBOM, does not verify the `sha256`, and does not certify the claim — the
correctness of provenance is the declarer's responsibility. `manifest_attestation`
surfaces only the *strength* of the claim. `unknown` is an accepted, meaningful
country value.

### 2.10 `connectivity` (optional — RFC-0006)

Opt-in declaration of the abstract **link roles** the robot supports. Absent
(and no envelope link-loss rule requiring a role) ⇒ connectivity checks are a
no-op.

```yaml
connectivity:
  links:
    - role: command_link              # command_link | telemetry_link | peer_link | payload_link
      required_for_operation: false
      autonomous_when_lost: false
      max_outage_seconds: <number|null>
      assurance_class: best_effort    # best_effort < monitored < assured < safety_critical
      description: <string>
```

A link **role** is an abstraction; the transport medium that carries it
(WiFi, 5G, RF, fibre) is Layer 0 and is deliberately **not** modelled — a
manifest that named a radio would fail the substrate-neutrality acid test.
`assurance_class` is ordered (low→high) so a future regulatory floor can
require `>= assured` additively. Roles MUST be unique within `links`.
`peer_link` is declarable now with no behavioural semantics (it makes the
future multi-robot RFC additive). The deployment-time counterpart — what the
robot does when a link is lost — is the safety envelope's `link_loss_policy`
(a list of `{role, action, max_outage_seconds?}`), validated against this
block at Pass 2 (role existence) and Pass 3 (action coherence).

## 3. What the validator enforces against the manifest

- **Pass 1** — the manifest schema parses (`extra: forbid`; types, enums,
  numeric bounds as in §2).
- **Pass 2** — capability checks: each primitive's required block/field is
  present; named locations/frames/events/endpoints/stations resolve;
  RFC-0006 governed link roles exist.
- **Pass 3** — safety envelope: manifest limits conjoined with the active
  envelope (strictest wins), including geofence/altitude/occupancy and
  RFC-0006 link-loss-rule action coherence.
- **Pass 5** — compliance policy over `provenance` (per `policy.md`); skipped
  when `provenance` is absent.

(Pass 4 is variable bindings — a Layer-3 concern, not manifest-driven.)

## 4. Conformance points

- Every required field present; declared limits internally consistent
  (`max_velocity` finite and ≥ 0; gripper `force_max_n` > 0; etc.) — enforced
  by the schema.
- The validator rejects programs that exceed declared capability or violate
  the conjoined envelope.
- Per-block coverage of spec → schema → consumer → conformance fixture →
  runnable example is tracked in
  [`docs/spec-coverage.md`](../../docs/spec-coverage.md).

## 5. What is and is not enforced in v0.1 (honest reconciliation)

The README's "what goes here when this document is drafted" listed two items
the shipped schema does **not** implement; stated plainly so the spec does not
over-promise:

- **URDF/SDF cross-reference.** The manifest has no field referencing a URDF,
  and the validator performs no manifest↔URDF frame consistency check. The
  capability layer is independent of kinematic structure in v0.1. A future RFC
  may add an optional `urdf_ref:`; until then, frames are self-declared and
  self-consistent only.
- **Safety-envelope schema.** Specified separately (deployment-time;
  `envelope.py` + the profile defaults), not part of `CapabilityManifest`.
  Layer 1 references it (§1.2); it is not in this document.

Also: HBOM content is opaque (not parsed), the integrity hash is recorded but
not verified, and `manifest_version` accepts only `"0.1"`. These are
deliberate v0.1 scope lines, candidates for future RFCs, not hidden gaps.
