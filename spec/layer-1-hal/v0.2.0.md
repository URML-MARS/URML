# URML Layer 1 — Hardware Abstraction (Capability Manifest) — v0.2.0

**Spec version:** 0.2.0 (pre-stable; per-artifact semver, breaking changes
allowed before 1.0.0)
**Status:** Normative. This is the specification document for Layer 1.
**Originating decision records:** The base manifest tracks
[RFC-0002](../../docs/rfcs/0002-initial-primitive-vocabulary.md)
(`manifest_version: "0.1"`). The `provenance:` block was added by
[RFC-0003](../../docs/rfcs/0003-us-alignment.md) /
[RFC-0004](../../docs/rfcs/0004-compliance-policy.md); its compliance-policy
evaluation is specified normatively in the sibling
[`policy.md`](policy.md). The `connectivity:` block was added by
[RFC-0006](../../docs/rfcs/0006-connectivity-and-link-loss.md). The fleet
`roster`, frame `transform`s, and operational `clearance` (§2.1, §2.4, §6)
were added by [RFC-0286](../../docs/rfcs/0286-multi-robot-fleet-addressing.md)
(multi-robot fleet addressing),
[RFC-0290](../../docs/rfcs/0290-frame-transform-graph.md) (frame-transform
graph), and [RFC-0291](../../docs/rfcs/0291-utm-strategic-deconfliction.md)
(UTM strategic deconfliction). This document is the consolidated normative
statement of the manifest schema, transcribed from the shipped validator.

**Changes since v0.1.0.** Additive, backward-compatible items: an optional
`transform` on a `frame` (§2.1), an optional `clearance` on `mobility` (§2.4),
the new §6 fleet roster, two legged `drive_type` values (`quadruped`, `biped`)
from [RFC-0009](../../docs/rfcs/0009-legged-humanoid-mobility.md) (§2.4), an
optional `arms` list on `manipulation` from
[RFC-0010](../../docs/rfcs/0010-whole-body-bimanual-manipulation.md) (§2.5),
optional `validation` ([RFC-0381](../../docs/rfcs/0381-simulation-fidelity-manifest-hints.md), §2.11) and `learned_policy` ([RFC-0383](../../docs/rfcs/0383-learned-policy-training-envelope.md), §2.12) blocks, and an optional `whole_body` block ([RFC-0384](../../docs/rfcs/0384-whole-body-capability-declaration.md), §2.13). A
v0.1.0 manifest validates unchanged under v0.2.0; the new fields are opt-in and
`manifest_version` remains `"0.1"`.

## 1. Scope and conventions

Layer 1 is how a robot **declares what it can do**. A URML-compatible robot
ships one *capability manifest*: a small, machine-readable document the
validator consumes (alongside a program and a safety envelope) to decide,
before any actuator moves, whether this robot can execute a given program.

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY**
are to be interpreted as in RFC 2119.

Layer 1 is a thin capability layer **on top of** existing structure standards,
not a replacement for them. It is substrate-neutral: a robot running ROS 2,
PX4, AUTOSAR, OPC UA Robotics, or a vendor SDK declares the same capabilities
the same way. It declares *baseline* capability, not runtime state, not sensor
data, not world-model contents, and not what a primitive does (Layer 2) or how
behaviors compose (Layer 3).

The canonical surface is YAML. Every model below forbids unknown fields
(`extra: forbid`): a manifest with an undeclared key is rejected, not
silently ignored.

### 1.1 Shared types

- **Identifier** — a string matching `^[a-z][a-z0-9_]*$`, length 1–64
  (snake_case). Used for every `name`/`id`/role.
- **Pose** — `{x, y, z?, yaw?, pitch?, roll?}`; `x` and `y` are required, the
  rest optional. Always interpreted in a named `frame`.
- **Transform** — `{translation: {x, y, z}, rotation: {roll, pitch, yaw}}`, a
  rigid-body (SE(3)) pose. Translation components are metres (default 0);
  rotation components are radians (default 0), applied in ZYX order
  (`yaw`, then `pitch`, then `roll`). Added by RFC-0290; used by `frame.transform`
  (§2.1) and a roster `anchor` (§6.2).

### 1.2 Manifest envelope vs. safety envelope (a boundary)

This document specifies the **capability manifest** — the robot's
self-declaration. The **safety envelope** is a separate, deployment-time
artifact (its schema is `envelope.py`, its defaults documented per profile in
[`spec/profiles/`](../profiles/)). The validator's Pass 3 conjoins manifest
limits with the active envelope (strictest wins). Layer 1 references the
envelope; it does not contain it. The README's older "what goes here" list
folded the envelope schema under Layer 1; the shipped split is as stated here.

## 2. The capability manifest

```yaml
manifest_version: "0.1"     # fixed; only "0.1" is accepted in this spec version
robot_id: <identifier>      # required
description: <string>       # optional

frames: [ ... ]             # declared coordinate frames
declared_locations: [ ... ] # named places in the world model
declared_events: [ ... ]    # event identifiers wait_for / link rules may name

mobility: { ... }           # optional capability block
manipulation: { ... }       # optional capability block
perception: { ... }         # optional capability block
programs: [ ... ]           # optional; substrate-declared programs (RFC-0015)

docking_stations: [ ... ]   # declared stations and their services
outputs: { named_endpoints: [ ... ] }   # report destinations

provenance: { ... }         # optional; RFC-0004 compliance (see policy.md)
connectivity: { ... }       # optional; RFC-0006 abstract link roles
validation: { ... }         # optional; RFC-0381 simulation-fidelity hints
learned_policy: { ... }     # optional; RFC-0383 learned-controller training envelope
whole_body: { ... }         # optional; RFC-0384 whole-body structure + stability limits
```

`manifest_version` MUST be the literal `"0.1"`. `robot_id` MUST be present.
All capability blocks are individually optional; a program that uses a
primitive whose capability the manifest does not declare is rejected at Pass 2
with a structured error naming the primitive, the missing field, and the
suggested addition.

### 2.1 `frames`

A list of declared coordinate frames. Each: `name` (Identifier), optional
`parent` (Identifier; the root frame has `parent: null`), and optional
`transform` (a Transform, §1.1; RFC-0290). The `transform` is this frame's
rigid-body pose **in its parent**: a point `p` here maps to the parent as
`R·p + t`. With transforms declared up the parent chain, a pose in any
connected frame can be expressed in any other (cross-frame geometry), which is
what lets a fleet compare one member's target against another's even when their
frame names differ (§6.2). A frame with a `parent` but no `transform` keeps the
v0.1 behavior: named, not geometrically placed. Every `frame` referenced by a
`pose`, a `declared_location`, or a `docking_station` MUST resolve to a
declared frame. URML does **not** in v0.2 cross-check frames against a
referenced URDF/SDF (see §5).

### 2.2 `declared_locations`

Named places programs reference by name (`move_to: { location: kitchen }`).
Each: `name`, `pose`, `frame`, optional `description`. A named location used
by a program MUST resolve here (or against the active world model).

### 2.3 `declared_events`

A list of event Identifiers. `wait_for(condition.event: ...)` and an
RFC-0006 link-loss rule may only name events declared here.

### 2.4 `mobility`

Required by `move_to`, `dock`, `hover`, `scan` (area survey), and
profile-specific motion. Fields:

- `drive_type` — one of `differential`, `omnidirectional`, `ackermann`,
  `tracked`, `multirotor`, `fixed_wing`, `vtol`, `manipulator_base`,
  `underwater_thrusters`, `quadruped`, `biped` (the last two added by
  [RFC-0009](../../docs/rfcs/0009-legged-humanoid-mobility.md) for legged and
  humanoid platforms).
- `max_velocity` — m/s, ≥ 0, required.
- `max_payload` — kg, ≥ 0, optional.
- `station_keeping` — bool (default `false`); MUST be `true` for `hover`.
- `service_ceiling` — m, ≥ 0, optional; required for aerial profiles and
  checked by `take_off` / aerial `scan`.
- `clearance` — optional (RFC-0291). The robot's **operational volume** for
  cross-robot deconfliction: a lateral footprint circle of `radius_m` (> 0) and
  a vertical band of `±vertical_m` (≥ 0 — altitude for aerial robots, depth for
  underwater robots, typically 0 for ground robots). Absent ⇒ the fleet
  collision check (§6.3) falls back to name-based comparison for this member
  rather than reasoning geometrically.

### 2.5 `manipulation`

Required by `grasp`, `release`, `bimanual`. Fields: `arm_count` (int ≥ 0);
`grippers` (list); `arms` (list, optional — RFC-0010); `reachable_workspace_m`
(≥ 0, optional). Each **Gripper**: `name`; `kind` ∈
`pneumatic | servo_electric | vacuum | magnetic | compliant`; `force_min_n`
(≥ 0); `force_max_n` (> 0); `accepted_classes` (list of Identifiers); `movable`
(bool, default `true`). `grasp` is rejected unless a gripper's declared force
range contains the requested force and its `accepted_classes` contains the
target's object class.

`arms` is the richer, optional form of `arm_count`
([RFC-0010](../../docs/rfcs/0010-whole-body-bimanual-manipulation.md)): each
**Arm** declares a `name` (Identifier) and a `gripper_ref` (the `name` of a
declared gripper). When present it lets a program address a specific arm by
name on `grasp`/`release` (`arm:`) and is required by the `bimanual` primitive,
which needs two arms (`arm_count >= 2` or two declared `arms`). Each
`gripper_ref` MUST resolve to a declared gripper; arm names MUST be unique;
when `arms` is given it SHOULD have `len(arms) == arm_count`. `arm_count` alone
remains valid for anonymous multi-arm addressing (`left`/`right`).

### 2.6 `perception`

Required by `detect`, `scan`, `measure`, `capture`, and
`wait_for(condition.sensor_threshold: ...)`. Fields:

- `cameras` — each: `name`, `movable` (default `false`), `supports_photo`
  (default `true`), `supports_video`/`supports_stream` (default `false`),
  `max_resolution`. `capture(target: ...)` against a fixed camera is rejected
  statically.
- `sensors` — each: `name`; `measurement_type` ∈ `distance | temperature |
  weight | pressure | humidity | depth | wind_speed | current | voltage |
  speech | point_cloud | custom`; optional `range_min`/`range_max`/`units`.
  Optional **capability** fields added by [RFC-0039](../../docs/rfcs/0039-sensor-schema-v0-2-iteration.md):
  `beam_count` (lidar-SKU-fixed beam count), `channels` (free-form list of
  data channels the sensor publishes, e.g. `range, intensity, reflectivity,
  near_ir`), `time_sync_methods` (free-form list of supported timestamping
  methods, e.g. `ptp, nmea, ieee_1588, ntp`), `rate_hz_max` (declared
  sample-rate ceiling). These declare *what the sensor can do*; the
  substrate driver picks the active mode at deployment time (Ouster's
  `LidarMode` + `UDPLidarProfile`, ROS 2 driver parameters, vendor
  configuration files). URML does not reach into substrate configuration.
- `object_vocabulary` — Identifiers `detect.object` MUST be drawn from.

### 2.7 `docking_stations`

Each: `name`, `pose`, `frame`, `services` (list of Identifiers; default
`["park"]`). Core services: `park`, `charge`; profile-extensible
(`swap_battery`, `swap_tool`, …). `dock(at, service)` is rejected unless the
target station declares the requested service.

### 2.8 `outputs`

`named_endpoints` — Identifiers a `report(to: <endpoint>)` may target. `user`,
`log`, and `caller` are universal and need no declaration; `speak` requires
`speech` declared here.

### 2.8a `programs` (optional — RFC-0015)

A list of substrate-declared programs the robot exposes by name, for the
`call_program` primitive. Each: `name` (Identifier), optional `description`,
and an optional `args` signature (a list of `{name, type}` where `type` is
`string`, `number`, or `boolean`). `call_program(name)` is rejected unless a
matching program is declared (`capability.missing_program`); passed `args` are
checked against the declared signature (`capability.program_arg_mismatch`).
The URML-facing `name` is a manifest identifier the adapter maps to the real
on-substrate routine (a Kawasaki AS program, an OPC UA method node), exactly as
`declared_locations` names map to poses. Absent ⇒ no program may be called.

### 2.9 `provenance` (optional — RFC-0004)

Opt-in hardware-provenance declaration. **Absent ⇒ Pass 5 is a no-op for the
manifest** (compliance enforcement is opt-in; the default validator ships
US-federal rules active, but a manifest that does not opt in is exempt).

```yaml
provenance:
  manifest_attestation: self_declared   # self_declared | third_party_audited | cryptographically_signed
  attestation_uri: <uri|null>
  components:
    - id: <identifier>
      role: critical                    # critical | non_critical | informational
      vendor: <string>
      country_of_origin: <ISO-3166-1-alpha-2 | unknown>
      country_of_final_assembly: <ISO-3166-1-alpha-2 | unknown>
      hbom_ref:                         # optional
        format: <string>               # e.g. cyclonedx-1.7
        uri: <uri>
        sha256: <64-hex | null>        # required when uri is local
```

The *policy* evaluated against this block (which countries/attestations/roles
pass) is specified normatively in [`policy.md`](policy.md); it is not
re-specified here. What URML does **not** do, normatively: it does not fetch
the HBOM, does not verify the `sha256`, and does not certify the claim — the
correctness of provenance is the declarer's responsibility. `manifest_attestation`
surfaces only the *strength* of the claim. `unknown` is an accepted, meaningful
country value.

### 2.10 `connectivity` (optional — RFC-0006)

Opt-in declaration of the abstract **link roles** the robot supports. Absent
(and no envelope link-loss rule requiring a role) ⇒ connectivity checks are a
no-op.

```yaml
connectivity:
  links:
    - role: command_link              # command_link | telemetry_link | peer_link | payload_link
      required_for_operation: false
      autonomous_when_lost: false
      max_outage_seconds: <number|null>
      assurance_class: best_effort    # best_effort < monitored < assured < safety_critical
      description: <string>
```

A link **role** is an abstraction; the transport medium that carries it
(WiFi, 5G, RF, fibre) is Layer 0 and is deliberately **not** modelled — a
manifest that named a radio would fail the substrate-neutrality acid test.
`assurance_class` is ordered (low→high) so a future regulatory floor can
require `>= assured` additively. Roles MUST be unique within `links`.
`peer_link` is the role a member MUST declare to participate in a `barrier`
(§6.3; RFC-0006 reserved it for exactly this multi-robot use). The
deployment-time counterpart — what the robot does when a link is lost — is the
safety envelope's `link_loss_policy` (a list of
`{role, action, max_outage_seconds?}`), validated against this block at Pass 2
(role existence) and Pass 3 (action coherence).

### 2.11 `validation` (optional, RFC-0381)

An optional block recording the simulation-validation context for the
deployment. Two closed-enum fields, both advisory:

```yaml
validation:
  terrain_fidelity: deformable                 # rigid | deformable | granular | unmodeled
  simulator_target_class: high_fidelity_multibody
                                               # kinematic | rigid_body | high_fidelity_multibody | photoreal | hardware
```

`terrain_fidelity` names the terrain class the deployment runs over. A
simulation reference runtime reads it to select a terrain model (a Chrono
runtime picks a deformable-terrain patch for `deformable`). `simulator_target_class`
names the fidelity tier the intent was validated against, so a fixture's
"validated" claim is precise rather than ambiguous.

Both fields are optional and neither gates a primitive. The validator
enforces only enum membership (an unknown value fails to parse, the same
closed-enum discipline as `substrate.autopilot_class`); it does not
simulate and does not assert the declared fidelity is true. Enforcement of
fidelity is the simulator's job, not the static gate's. Enum growth is
RFC-gated.

### 2.12 `learned_policy` (optional, RFC-0383)

When the substrate is a learned controller (a neural locomotion or
manipulation policy), its real limit is not a mechanical maximum but the edge
of its training distribution. An optional `learned_policy` block declares that
distribution so the validator can refuse a deployment whose admissible intent
exceeds what the policy was trained for:

```yaml
learned_policy:
  policy_ref: "isaac-lab://anymal-flat-v3"     # opaque handle; documentation, not parsed
  command_ranges:
    - { quantity: linear_velocity_x, min: -0.5, max: 1.0, unit: m_per_s }
    - { quantity: yaw_rate,          min: -1.0, max: 1.0, unit: rad_per_s }
  terrain_classes: [rigid, deformable]          # RFC-0381 terrain vocabulary
  payload_range: { min: 0.0, max: 5.0, unit: kg }
  enforcement: reject                           # reject | warn
```

The validator checks the deployment's admissible ceiling, the strictest of the
mechanical `mobility` limit and the safety-envelope cap, against the trained
command and payload ranges, and the declared `validation.terrain_fidelity`
against the trained `terrain_classes`. A ceiling above the trained maximum, or
a terrain outside the trained set, is an error when `enforcement: reject` and a
warning when `enforcement: warn`. The validator never loads or runs the policy;
`policy_ref` is opaque, and how a training framework exports these limits is
out of scope. Per-primitive intent-to-command inference is a documented
follow-on.

### 2.13 `whole_body` (optional, RFC-0384)

A legged / humanoid robot is more than a `drive_type` label and a set of arms:
it has a kinematic structure (legs, arms, torso) and a stability envelope. An
optional `whole_body` block declares both, so the validator can check structural
consistency and a static-stability declaration, and gate a carry-while-moving
request. It is the locomotion-side complement to `manipulation.arms` (RFC-0010):

```yaml
whole_body:
  chains:                       # the robot's kinematic chains (limbs)
    - { name: left_leg,  kind: leg,   dof: 6 }
    - { name: right_leg, kind: leg,   dof: 6 }
    - { name: left_arm,  kind: arm,   dof: 7, arm_ref: left }   # binds to manipulation.arms
    - { name: right_arm, kind: arm,   dof: 7, arm_ref: right }
    - { name: torso,     kind: torso, dof: 1 }
  static_stable: true           # can hold a pose without continuously stepping
  can_carry_while_moving: true  # can locomote while holding a payload
  max_incline_deg: 15.0         # steepest ground incline it can traverse
  max_tilt_deg: 10.0            # max body tilt tolerated while stable
  center_of_mass: { x: 0.0, y: 0.0, z: 0.9 }    # nominal CoM, body frame (m)
  support_polygon:              # nominal support footprint, body frame (m), >= 3 vertices
    - { x: -0.20, y: -0.15 }
    - { x:  0.20, y: -0.15 }
    - { x:  0.20, y:  0.15 }
    - { x: -0.20, y:  0.15 }
```

Each **KinematicChain** has a `name`, a `kind` ∈ `leg | arm | torso | head | other`,
a `dof` (≥ 1), and an optional `arm_ref` (only on `kind: arm`) naming the
`manipulation.arms[]` entry that chain realizes. Every field is a **static
declaration**, not live state: URML declares the structure and the stability
limits a request is validated against; realizing balance is the substrate's job
(the RFC-0010 line). The richer stability fields earn their place by being
checked, not by being decorative.

The validator enforces: a leg-chain count matching a legged `drive_type`
(`biped` = 2, `quadruped` = 4); each arm chain's `arm_ref` resolving to a
declared arm; a declared `center_of_mass` lying within the declared
`support_polygon` (static-stability consistency); and a `move_to(carrying: …)`
on a legged platform with `can_carry_while_moving: false` is rejected. Error
codes: `capability.whole_body_inconsistent`, `capability.whole_body_unstable_com`,
`capability.cannot_carry_while_moving`. The block is optional and fully additive;
a manifest without it behaves exactly as before.

## 3. What the validator enforces against the manifest

- **Pass 1** — the manifest schema parses (`extra: forbid`; types, enums,
  numeric bounds as in §2).
- **Pass 2** — capability checks: each primitive's required block/field is
  present; named locations/frames/events/endpoints/stations resolve;
  RFC-0006 governed link roles exist.
- **Pass 3** — safety envelope: manifest limits conjoined with the active
  envelope (strictest wins), including geofence/altitude/occupancy and
  RFC-0006 link-loss-rule action coherence.
- **Pass 5** — compliance policy over `provenance` (per `policy.md`); skipped
  when `provenance` is absent.

(Pass 4 is variable bindings — a Layer-3 concern, not manifest-driven.) A
multi-robot program runs all of the above per member and then the cross-robot
fleet checks of §6.3.

## 4. Conformance points

- Every required field present; declared limits internally consistent
  (`max_velocity` finite and ≥ 0; gripper `force_max_n` > 0; `clearance.radius_m`
  > 0; etc.) — enforced by the schema.
- The validator rejects programs that exceed declared capability or violate
  the conjoined envelope.
- Per-block coverage of spec → schema → consumer → conformance fixture →
  runnable example is tracked in
  [`docs/spec-coverage.md`](../../docs/spec-coverage.md).

## 5. What is and is not enforced in v0.2 (honest reconciliation)

The README's "what goes here when this document is drafted" listed two items
the shipped schema does **not** implement; stated plainly so the spec does not
over-promise:

- **URDF/SDF cross-reference.** The manifest has no field referencing a URDF,
  and the validator performs no manifest↔URDF frame consistency check. The
  capability layer is independent of kinematic structure in v0.2. A future RFC
  may add an optional `urdf_ref:`; until then, frames are self-declared and
  self-consistent only.
- **Safety-envelope schema.** Specified separately (deployment-time;
  `envelope.py` + the profile defaults), not part of `CapabilityManifest`.
  Layer 1 references it (§1.2); it is not in this document.

Also: HBOM content is opaque (not parsed), the integrity hash is recorded but
not verified, and `manifest_version` accepts only `"0.1"`. These are
deliberate scope lines, candidates for future RFCs, not hidden gaps. The fleet
deconfliction of §6 is **strategic** (static, pre-execution), not a live
collision-avoidance loop — see §6.4.

## 6. Fleets: roster, shared frames, and deconfliction (RFC-0286/0290/0291)

A single capability manifest describes one robot. A **fleet roster** describes
several, and is the multi-robot analogue of the manifest: it binds N
already-valid per-robot manifests by a short, English-callable handle. The
roster does not nest or alter a manifest; `CapabilityManifest` is unchanged. A
fleet program is a two-document YAML form — the roster, then an ordinary
Layer-3 program whose `on:`/`barrier:` nodes (Layer 3 §2.5–2.6) address the
handles:

```yaml
roster_version: "0.1"
world_frame: site          # optional (RFC-0290): the fleet's shared world frame
shared_frames: [site]      # optional (RFC-0291): frames denoting ONE physical reference across members
members:
  - { name: courier, manifest: husky_amr }
  - { name: arm,     manifest: kawasaki_rs,
      anchor: { frame: base, transform: { translation: {x: 4.0, y: 0.0}, rotation: {yaw: 1.5708} } } }
---
profile: industrial
behavior: { ... }          # an ordinary Layer-3 tree addressing the handles
```

### 6.1 Roster

- `members` — at least one. Each member: `name` (an Identifier handle, unique
  within the roster — two robots cannot share a handle) and `manifest` (an
  opaque reference, a registry name or path, the caller resolves to a
  `CapabilityManifest` before validation; the roster never loads it), plus an
  optional `anchor` (§6.2).
- `world_frame` — optional Identifier; the shared frame a member's `anchor`
  places it into (§6.2).
- `shared_frames` — optional list of Identifiers naming frames that denote one
  common physical coordinate reference across all members (e.g. `site`,
  `water`, `agl`). Entries MUST be unique. The geometric collision check
  (§6.3) compares only targets whose frame is shared; a member's private local
  frame is never compared against another's. Empty (default) ⇒ the cross-robot
  check abstains.

### 6.2 Shared frames and anchors (RFC-0290)

Two members can refer to the same frame by name (`shared_frames`, the simple
same-name path), or place one of their own frames into the `world_frame` with
an `anchor` (`{frame, transform}`, the site-survey path). An anchor's
`transform` is the SE(3) pose of §1.1. With anchors, members whose frame names
differ (a drone's `agl`, a rover's `site`) still resolve their targets into one
world and can be compared geometrically.

### 6.3 What `validate_fleet` enforces

A fleet program runs every single-robot pass (§3) per member, re-keyed by
handle, and adds cross-robot checks before any actuator moves — precisely what
no single vendor SDK can catch, because none sees more than its own robot:

- `fleet.undeclared_member` — an `on:`/`barrier:` names a handle the roster
  does not declare (or, in a multi-member fleet, a step sits outside any `on:`
  scope).
- `fleet.capability_unsupported_on_member` — a primitive scoped to a member
  whose manifest fails the ordinary per-robot capability check (§3, Pass 2).
- `fleet.concurrent_shared_workspace` — two members are driven to the same
  place at the same time inside one `parallel`. The check is **geometric** when
  both declare a `clearance` and share world coordinates (volumes overlap
  unless separated laterally by footprint, vertically by altitude/depth band,
  by medium via `drive_type`, or in time by a `barrier`), and **name-based**
  (same declared-location name) when no `clearance` is declared.
- `fleet.barrier_missing_peer_link` — a `barrier` names a member that does not
  declare the `peer_link` connectivity role (§2.10).
- `fleet.shared_frame_undeclared` / `fleet.anchor_frame_undeclared` — a
  `shared_frames` entry or an `anchor.frame` names a frame the relevant member
  does not declare.

### 6.4 What fleet validation does and does not do (honest reconciliation)

This is **strategic deconfliction**: the validator rejects a plan that would
put two robots in the same volume at the same instant, statically, before
execution. It is **not** a live collision-avoidance loop (no runtime sensing or
replanning) and **not** a building-scale traffic manager; continuous,
facility-wide multi-robot routing is Open-RMF's domain, and URML composes above
it. Absent a `clearance` or any `shared_frames`, the geometric check abstains
and falls back to name-based comparison rather than guessing at geometry.

The worked examples are the fleet conformance fixtures
([`conformance/fixtures/fleet/`](../../conformance/fixtures/fleet/)): a
courier-to-arm handoff, ground footprint overlap, air vertical separation, and
water depth separation, each validated (and the positive ones executed)
hermetically.

## 7. Versioning

This document is `layer-1-hal@0.2.0`. Pre-`1.0.0`, breaking changes are
allowed but MUST go through an RFC that updates this document (and, for the
provenance/connectivity/fleet blocks, the originating RFC) in the same change.
The v0.2.0 additions over v0.1.0 (`frame.transform`, `mobility.clearance`, the
fleet `roster`) are additive and optional; `manifest_version` stays `"0.1"`.
