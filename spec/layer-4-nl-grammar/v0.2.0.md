# URML Layer 4 — Natural Language Interface (Prompt Contract) — v0.2.0

**Spec version:** 0.2.0 (pre-stable; per-artifact semver, breaking changes
allowed before 1.0.0)
**Status:** Normative. This is the specification document for Layer 4.
**Originating decision records:** Layer 4 has no dedicated RFC. It is the
published *prompt contract* implemented in
[`reference/llm-bridge/`](../../reference/llm-bridge/) (part of the
[Core Commitment](../../CORE_COMMITMENT.md) — always Apache 2.0, no vendor
coupling) and described informally in this layer's README. The fleet
(multi-member) assembly of §2.5 was added by
[RFC-0286](../../docs/rfcs/0286-multi-robot-fleet-addressing.md). This document
is the normative statement of the contract, transcribed from the shipped
bridge.

**Changes since v0.1.0.** One additive section, §2.5: a roster-aware system
prompt and a fleet revision loop for translating a request into a multi-robot
program. The single-robot contract (§2.1–2.4, §3) is unchanged.

## 1. Scope and conventions

Layer 4 is the documented, provider-neutral way for any large language model
to translate a natural-language request into a *validated* URML program. URML
does **not** parse natural language: the LLM does the language work; Layer 4
gives it a precise target and a deterministic correction loop so the result is
reliable. Layer 4 does not execute URML (that is the runtime), does not own
the world model, and is not a formal grammar of the input language — it
specifies the *output* contract and the loop around it.

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY**
are to be interpreted as in RFC 2119.

Provider neutrality is **structural and non-negotiable** (CLAUDE.md §What
Claude Should Never Do): the contract MUST NOT privilege any vendor. Anthropic,
OpenAI, open-weights (Llama/Mistral/Qwen via vLLM/llama.cpp/Ollama), and
on-device models are all first-class. Adding a provider MUST be a small adapter
file, never a change to the bridge.

## 2. The contract surface

A conformant Layer-4 integration assembles a **system prompt** from exactly
these parts, in this order (`prompt.py: build_system_prompt`):

1. **Instruction header** — a stable, opaque string stating: emit a single
   JSON object conforming to the attached schema; no Markdown fences; no
   commentary outside the JSON; use only manifest-declared
   primitives/locations/frames/objects/sensors/services; if the request needs
   an undeclared capability, emit a `report` step with `status: failure` and a
   `facts.reason` rather than fabricating capability; respect the envelope.
2. **Active profile(s)** — informational.
3. **Capability-manifest summary** — a compact, prompt-friendly rendering of
   the Layer-1 manifest (§2.1).
4. **Safety-envelope summary** — when an envelope is active (caps, geofence
   count, occupancy zones, weather thresholds, link-loss policy).
5. **Few-shot examples** — zero or more `(user_request, target_program)`
   pairs (§2.2).
6. **The URML program JSON Schema** — `export_schema("program")` from
   `urml_validator`, serialized deterministically (sorted keys). This is the
   single source of structural truth; the bridge does not maintain a second
   copy.
7. **Revision context** — present only on a revision attempt (§3).

The header is deliberately stable to keep prompt-cache hit rates predictable.
The manifest/envelope summaries intentionally drop free-form metadata so an
identical robot yields an identical prefix.

### 2.1 What the model MAY reference

Only what the manifest declares: declared locations, frames, declared events,
mobility/manipulation/perception capabilities, docking-station services,
output endpoints, declared programs (RFC-0015 `call_program`), and (RFC-0006)
connectivity roles. A request that requires anything undeclared MUST yield a
`report(status: failure)` explaining what is missing — the model MUST NOT
invent capability. In particular the model MUST NOT emit `call_program` for a
program the manifest does not declare, and SHOULD prefer modelled primitives
over `call_program` whenever the intent is expressible with them; the opaque
program call is the substrate-specific last resort, not a shortcut.

Under the research-grade `av` profile (RFC-0020), "drive to / take me to" intents
map to a `plan_path` (compute a trajectory, bind it) followed by a
`follow_trajectory` (execute it) — never to `move_to`, which is "go to a named
pose," not "plan and drive a route." The model emits `plan_path` only when the
manifest declares `av.hd_map`.

### 2.2 Few-shot library

`few_shot.py` ships profile-scoped sets (`home_few_shots`,
`industrial_few_shots`, `drone_few_shots`, `fleet_few_shots`) and a selector
`few_shots_for(profiles)` (empty or all-unknown profiles fall back to the home
set; multiple profiles concatenate in order). Each `FewShot` is a
`(user, program, note?)` triple whose `program` validates against the matching
manifest fixture (or roster, for the fleet set). The paired
natural-language/URML scenario files in [`examples/`](../../examples/) are the
human-facing form of the same contract (`<scenario>.en.txt` ↔
`<scenario>.urml.yaml`).

### 2.3 Grammar-constrained providers (RFC-0021)

A provider MAY enforce structural validity at decode time using a GBNF
grammar derived from the program JSON Schema. When it does, the JSON
Schema remains the single source of structural truth: the GBNF is a
derivation, not a parallel specification, and a structurally grammar-valid
emission is still subject to the full validator (the grammar enforces JSON
shape; the validator enforces semantics — `pattern`, `minLength`, numeric
ranges, cross-field constraints, manifest-aware checks). The reference
derivation is `grammar.schema_to_gbnf()` in
[`reference/llm-bridge/`](../../reference/llm-bridge/); a provider that
implements its own grammar derivation MUST produce a grammar consistent
with the exported program schema. A provider that does not constrain
decoding (e.g., cloud providers using tool-use or JSON mode) is unaffected
by this section.

### 2.4 On-device model interchange (RFC-0021)

When a provider distributes a model file as part of its on-device path,
the file format is **GGUF**. This is a packaging contract, not a runtime
one: a provider that talks to an inference server over HTTP (the two
reference on-device adapters do) imposes no model-format requirement on
its callers, and a provider that does not distribute model files is
unaffected. The contract exists so that documentation, conformance
reports, and operator workflows can name a single interchange format when
they need to.

### 2.5 Fleet (multi-member) assembly (RFC-0286)

A multi-robot translation uses the same contract with one substitution: where
the single-robot prompt summarizes one manifest, the fleet prompt summarizes a
whole **roster** — one capability summary per member — and the loop validates
with `validate_fleet` instead of `validate`. The reference assembly is
`prompt.py: build_fleet_system_prompt` and the `FleetBridge` class; the
revision loop, provider protocol, and JSON-Schema-as-truth rule are all
identical to §2 and §3.

The fleet instruction header adds the multi-robot rules a conformant fleet
prompt MUST convey:

- Address one robot by wrapping its work in an `on` node
  (`{"type": "on", "member": "<roster member>", "body": <behavior-or-step>}`);
  every primitive MUST sit under an `on` node naming a declared roster member.
- Synchronize robots with a `barrier`
  (`{"type": "barrier", "members": [...]}`); execution does not pass a barrier
  until every named member reaches it. Use one whenever one robot must wait for
  another (a handoff, a rendezvous).
- Run robots at the same time by placing their `on` nodes in a `parallel`.
- Use only the declared members, and per member only that member's declared
  locations/objects/sensors/programs; a request no member can satisfy MUST
  yield a `report(status: failure)` under an `on` node, never invented
  capability.
- Do not drive two different members to the same declared location inside one
  `parallel`; separate them with a `barrier` or use distinct locations (the
  validator enforces this as `fleet.concurrent_shared_workspace`).

The emitted program is an ordinary Layer-3 tree (Layer 3 §2.5–2.6); the roster
it is validated against is the Layer-1 §6 artifact.

## 3. The validator-feedback revision loop

`Bridge.translate(user_request)` is the normative algorithm (`FleetBridge.translate`
is the identical loop with `validate_fleet` substituted for `validate`):

1. Build the system prompt; call `LLMProvider.complete(system, user, schema)`.
2. Parse the completion as a single JSON object. Non-JSON, empty, or
   non-object output is a `ProviderError` (providers MUST return raw JSON,
   never Markdown-fenced).
3. Run the full validator (`urml_validator.validate` / `validate_fleet`, all
   five passes plus, for a fleet, the cross-robot checks; policy per
   configuration).
4. If accepted → return the validated program with the revision count.
5. If rejected and **only `policy.*` errors remain** → raise
   `BridgePolicyViolation` immediately: a program cannot revise its way out of
   a hardware-provenance failure, so further attempts are not made (RFC-0004).
6. Otherwise, if revision budget remains, append a **revision context** (the
   prior raw emission plus the machine-readable non-policy errors —
   `{code, primitive, path, field, message, suggestion}`) and loop.
7. If the budget (`max_revisions`, default 3 → 4 attempts total) is exhausted
   → raise `BridgeRevisionExhausted` with the last `ValidationResult`.

The loop is **deterministic and bounded**: it terminates in at most
`max_revisions + 1` provider calls. Only actionable (non-policy) errors are
fed back; policy errors are surfaced terminally.

## 4. Conformance points

- The exported JSON Schema accepts every shipped example/few-shot program and
  rejects malformed programs (validator schema-export regression guard +
  `test_few_shot_library`).
- The revision loop reaches `accepted`, `BridgePolicyViolation`, or
  `BridgeRevisionExhausted` and nothing else, within the bound
  (`test_bridge`); the fleet loop does the same against a roster
  (`test_fleet_bridge`).
- The provider abstraction round-trips through a hermetic `EchoProvider`
  with no network (`test_bridge`, `test_translate_cli`); the runnable
  walkthrough is [`docs/demos/bridge-roundtrip.md`](../../docs/demos/bridge-roundtrip.md).
- Per-construct coverage is tracked in
  [`docs/spec-coverage.md`](../../docs/spec-coverage.md).

## 5. What is and is not in v0.2 (honest reconciliation)

The README and the llm-bridge README describe an **interactive
disambiguation protocol** — "the structured questions an LLM must ask the
user when ambiguous (which red mug?)". **This is not implemented.**
`Bridge.translate` is a one-shot emission plus the deterministic
validator-feedback loop of §3; there is no clarifying-question turn and no
user round-trip inside the bridge. Ambiguity is resolved by the header
instruction: the model picks a reasonable manifest-grounded default, or, when
the request needs undeclared capability, emits a `report(status: failure)`
naming what is missing. An interactive disambiguation protocol is a candidate
for a future RFC; until one accepts it, a conformant bridge MUST NOT be
expected to conduct a clarifying dialogue, and the spec does not imply one.

Also deliberately scoped:

- **Multilingual.** The *structure* reserves `<scenario>.<lang>.txt` slots for
  Hebrew/Spanish/Japanese/Mandarin; the shipped *content* is English-only.
  The contract itself is language-agnostic (the model does the language work);
  no schema or loop change is needed to accept non-English input.
- **The bridge does not execute URML.** It returns validated programs;
  handing them to a runtime is the caller's responsibility.

## 6. Versioning

This document is `layer-4-nl-grammar@0.2.0`. Pre-`1.0.0`, breaking changes are
allowed but MUST go through an RFC that updates this document in the same
change. The program JSON Schema is versioned with the validator; Layer 4 never
forks it.
