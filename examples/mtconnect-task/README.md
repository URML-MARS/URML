# A MOVE_MATERIAL task as a validated URML program, lowered to UR

For [mtconnect/cppagent Discussion #615](https://github.com/orgs/mtconnect/discussions/615)
(making MTConnect's Task model robot-agnostic).

MTConnect's Task model gives a `TaskType` such as `MOVE_MATERIAL`: it says *what* to
accomplish, but not what to do physically. Pinning the physical work to a URScript File
Asset gets you the "what" while re-pinning it to UR, which defeats the interoperability
of the tasks model.

URML's answer is to let the task reference a URML program as its work-to-be-done. The
program is substrate-agnostic, validated against the cell's capability manifest and
safety envelope, and only then lowered per-robot. For a UR arm the adapter emits
URScript; on another cell a different adapter emits something else.

## What it shows

The cell is the one described on #615: one arm tending three CNC machines
(`three-cnc-cell.manifest.yaml`). Three MOVE_MATERIAL programs run through
validate-then-lower:

1. **Admissible**: load a blank from the infeed bin into CNC 1. Validates, then lowers
   to an illustrative UR adapter sketch (`movej` to each declared pose, `rq_close` /
   `rq_open` for the gripper).
2. **Refused (undeclared machine)**: the same work targeting CNC 4, which the cell does
   not have. Refused with `capability.missing_location`, before any URScript is emitted.
3. **Refused (over the gripper cap)**: a grasp on a heavy billet at 250 N, over the
   60 N gripper. Refused with `envelope.force_exceeded`, before any URScript is emitted.

The invalid work never reaches the UR controller. That is the gate: a MOVE_MATERIAL
program is checked against the specific cell before it can become a machine command.

## Run it

```bash
python examples/mtconnect-task/move_material_task.py
```

Hermetic and deterministic (the validator only, no MTConnect, no UR, no robot). The
committed [`move-material-report.txt`](move-material-report.txt) is byte-asserted in CI.

## Honest altitude

The UR adapter output in the report is **illustrative and not generated by URML**. A
real UR adapter would drive the UR controller (RTDE or the UR ROS driver). It is shown
to make concrete where the per-robot, brand-specific lowering lives, and that it runs
only on a program URML has already validated.

URML validates and carries the structured intent; the per-robot adapter does the
URScript; URML does no motion planning and no control. It **contains** the
brand-specific layer behind a boundary, it does not make it vanish. So a MOVE_MATERIAL
task can carry an agnostic, checkable URML program as its work, and the UR-specific
URScript is an adapter output written once per robot family, not copied into every
task. No dependency on anything of MTConnect's.
