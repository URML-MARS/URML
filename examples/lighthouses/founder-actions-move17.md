**URML — Measurement-Science Feedback for NIST EL Intelligent Systems Division**

*Ido Yahalomi, URML maintainer · 2026-05-29*

URML (urml.dev) is a small, opinionated, human-readable language for describing robot intent, designed to sit above existing robot operating systems and compile to whatever runtime lives below. The spec is Apache-2.0 forever per its Core Commitment; the v0.1.0 release shipped on 2026-05-22 with a ROS 2 reference runtime, a conformance test suite, a validator (`urml validate --policy`), and a US-federal-aligned default policy file (NDAA Section 889, EO 14307, FCC Covered List).

URML's structure is four layers above the substrate:

- **Layer 1 — Hardware Abstraction (HAL):** the capability manifest declares what a robot can do (mobility class, manipulators, sensors, safety envelope).
- **Layer 2 — Intent Primitives:** verbs like `move_to`, `dock`, `pick_from`, `place_at`, `grasp`, `release`, `swap_tool`, `scan_area`, `query_detection`.
- **Layer 3 — Behavior Composition:** how primitives compose into sequences, branches, and recoveries.
- **Layer 4 — Natural Language Interface:** the grammar that lets a sentence in English (or Hebrew, Spanish, Japanese, Mandarin) compile to validated Layer-2 programs.

**Measurement-science fit.** URML's manifest + validator + conformance suite map onto NIST EL ISD's published performance categories cleanly:

| URML surface | NIST EL ISD performance category |
|---|---|
| `move_to`, `dock`, `scan_area` primitives + manifest mobility class | Mobility, agility |
| `pick_from`, `place_at`, `grasp`, `release`, `swap_tool` + manipulator declaration | Manipulation, agility |
| Sensor manifest (lidar, camera, radar, sonar) + perception primitives | Perception |
| `safety_envelope` manifest field + validator gate | Safety |

Two concrete intersection opportunities:

1. **MORT composability.** URML's `reference/ros2-runtime/` could be exercised against NIST's Modular Open-Source Robotics Testbed. The interesting measurement-science question is whether URML's static manifest validation correlates with measured runtime agility / safety scores — a hypothesis URML alone can't test but MORT is purpose-built to surface.

2. **ARIAC scenario expression.** URML's industrial profile (RFC-0013) defines `pick_from`, `place_at`, and `swap_tool` against an industrial-arm manifest. Several ARIAC competition scenarios can be expressed verbatim in URML; doing so would (a) give URML a published-scenario corpus for conformance work and (b) give the ARIAC community a candidate human-readable scenario notation as related art.

**URML's planned structural separation.** Per the project roadmap, the spec, conformance suite, validator, ROS 2 + PX4 reference runtimes, LLM bridge prompt contract, and US-federal default policy file are Apache-2.0 forever and non-negotiable (the Core Commitment). The realistic future foundation target is US-domiciled and US-aligned (a 501(c)(6) industry association, an SDO with strong US ties, or a sponsored project under an existing US-domiciled foundation). I'm currently engaging foundation candidates (OSRA, JDF) at the orientation level; NIST EL ISD as the US institutional home for robotics measurement standards is a natural relationship to warm in parallel.

2. Is there a NIST EL ISD path for an external project (URML) to compose reference runtimes against MORT and contribute measurement scenarios?
3. ARIAC URML-language framing: would expressing ARIAC scenarios in URML as related art be of interest, or is that out of scope for the competition format?

**URML — A Candidate Interoperability Layer for ASTM F45.04**

*Position paper to ASTM Committee F45 / Subcommittee F45.04 (System Communication and Interoperability)*

*Ido Yahalomi, URML maintainer · 2026-05-29*

**Abstract.** URML (Universal Robot Language, urml.dev) is a substrate-neutral, declarative, human-readable language for robot intent. URML's Layer-1 HAL capability manifest declares what a robot can do; its Layer-2 intent primitives declare what the operator wants done; a validator (`urml validate --policy`) enforces a static check between the two before execution. This position paper proposes URML's manifest + primitive schema as a candidate interoperability layer for ASTM F45.04 consideration, between substrate-side hardware abstractions (the OEM's SDK; ROS 2 messages; OPC UA Robotics NodeSet) and operator-side intent declaration (mission planners, NL interfaces, supervisory controllers). The paper outlines the interoperability problem URML targets, the concrete schema URML proposes, mapping notes to adjacent F45 subcommittee scopes, and three asks for F45.04 subcommittee orientation.

**1. The interoperability problem.** Production robotics deployments compose multiple runtime substrates simultaneously — ROS 2 for mobile-base coordination, PX4 for drone autopilots, MoveIt 2 for manipulation planning, DDS or Zenoh for transport, OPC UA Robotics for industrial-cell integration. Each substrate has its own capability declaration form (or none). An interoperability standard at the manifest + intent layer — declaring once what the robot can do, and what the operator wants, in a substrate-neutral notation — is the natural interoperability target above the OEM SDK boundary and below the operator interface.

**2. URML's interoperability proposal.** URML is layered:

- **Layer 1 — Hardware Abstraction (capability manifest).** A YAML schema declaring the robot's mobility class (mobile-base, drone, fixed-arm, legged), manipulator topology, sensor set, safety envelope, substrate class (ros2 / px4 / opc_ua_robotics), and policy posture.
- **Layer 2 — Intent Primitives.** A small set of verbs — `move_to`, `dock`, `scan_area`, `pick_from`, `place_at`, `grasp`, `release`, `swap_tool`, `query_detection` — with typed arguments and static preconditions.
- **Layer 3 — Behavior Composition.** Sequences, branches, recoveries, and timing modifiers.
- **Layer 4 — Natural Language Interface.** A formal grammar that compiles an English (or Hebrew / Spanish / Japanese / Mandarin) sentence to a validated Layer-2 program.

The interoperability boundary URML proposes for F45.04 standardization sits at **Layer 1 ↔ Layer 2**. The manifest declares the capability surface in a substrate-neutral form; the intent program references only primitives that the manifest declares the robot supports. The validator enforces this statically before dispatch.

URML is Apache-2.0 forever per its Core Commitment; the spec, conformance suite, validator, ROS 2 + PX4 reference runtimes, LLM bridge prompt contract, and US-federal-aligned default policy file remain open-source under that license. The intent of bringing URML's schema into ASTM F45.04 is to allow the committee to standardize the manifest + primitive boundary as a recognized interoperability layer, with URML's existing schema as a candidate starting point that the committee can adopt, modify, or reject on its merits.

**3. Mapping to adjacent F45 subcommittees.**

- **F45.02 (A-UGV Docking and Navigation):** URML's `move_to`, `dock`, `scan_area` primitives + manifest mobility-class declaration align with F45.02's navigation performance work; URML's manifest could declare F45.02-conformant navigation as a substrate capability.
- **F45.05 (Grasping and Manipulation):** URML's `pick_from`, `place_at`, `grasp`, `release`, `swap_tool` primitives align with F45.05's manipulation performance work; URML's industrial profile (RFC-0013) ships these primitives for industrial-arm deployments.
- **F45.06 (Legged Robot Systems):** URML's manifest mobility-class declaration includes `legged` as a value; the legged-specific primitive set is future work URML would benefit from F45.06 review on.

The natural cross-reference shape is: F45.04 standardizes the manifest + intent boundary; F45.02 / F45.05 / F45.06 standardize the substrate capability classes that the manifest declares. URML's schema is candidate raw material for F45.04 specifically.

**4. Composability with existing standards.** URML composes against:

- ROS 2 (URML's primary reference runtime; OSRA / OSRF governance).
- PX4 / MAVLink / MAVSDK (drone substrate; Linux Foundation Dronecode governance).
- OPC UA Robotics Companion Specification (industrial-cell substrate; OPC Foundation governance).
- MoveIt 2 (manipulation dispatcher; MoveIt Working Group governance).
- Nav2 (navigation dispatcher; ROS 2 Navigation Working Group governance).
- Fast DDS / Cyclone DDS (transport; eProsima + Eclipse Foundation governance).

URML's existing outreach to each of these substrates is documented in the URML repository under [`docs/rfcs/`](https://github.com/URML-MARS/URML/tree/main/docs/rfcs); the substrate-spine wave (RFCs 0196-0211) engaged the substrate maintainers explicitly to make URML's substrate-neutrality concrete rather than rhetorical.

**5. Asks for F45.04 subcommittee.**

1. Does URML's substrate-neutral manifest + Layer-1 / Layer-2 boundary match F45.04's interoperability mandate, or is the F45.04 scope different in ways URML should adjust framing to address?
2. What's the typical channel for an individual ASTM member to contribute a position paper + propose collaborative document development at F45.04?
3. Is F45.04 interested in scoping a URML-position-paper-driven standards-track document, or does the subcommittee prefer URML contribute to existing F45.04 documents?
4. What's the typical ASTM → ANSI → ISO PAS pickup path for F45 standards? URML's planned structural-separation arc would benefit from downstream pickup orientation.
